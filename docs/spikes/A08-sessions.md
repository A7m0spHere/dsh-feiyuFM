## 规则与实现

| MVP 要求 | 实现 |
|---|---|
| 多 Session 不抢占播放 | **三道独立闸门**：正在播放 → 一律拒绝；事件无 session 标识 → 拒绝；不是当前活动 Session → 拒绝。每种拒绝都有自己的原因，日志里能看到真实原因而不是笼统的失败 |
| 活动 Session 的定义 | 最近产生事件、且在 5 分钟窗口内的那个；**同一毫秒的两个事件**用单调序号打破平局（后记入者胜） |
| 注册表有界 | 30 分钟未见的会话被遗忘；最多跟踪 32 个；超限时淘汰最久未见者 |
| 暂停不被自动事件撤销 | 暂停后**任何** Session 事件都不能开始播放（测试断言 paused 保持 true） |
| 临时 Session 只少量沉淀 | 短于 10 分钟的会话按 **0.5 权重**计入长期偏好（其余情况 1.0） |
| 沉淀设上限 | 一个会话对同一首曲目**最多 8 次**更新；达到上限后拒绝并给出原因 |

**上限是自记的**：`session_influence` 表由成长逻辑自己累加，不依赖"谁记录了这次收听"，因此重启后仍然有效。这一点是测试逼出来的——最初版本从 `listen_history` 推断，导致**直接调用成长函数时上限永远不生效**（契约脆弱），已改为自包含。

## 真实 Session 标识：如实说明未验证

适配器需要从 `(session, event)` 的 session 对象里取一个稳定标识。**P0-01 探针当时没有记录该对象的字段名**，本机的类型声明也不在此 checkout 可读路径下，因此我**没有猜一个字段名**，而是：

- `sessionIdOf()` 依次尝试 `id` / `sessionId` / `key` / `identity`（含 getter 形式），再尝试一层嵌套的 `meta`/`info`/`state`；
- 都取不到时返回 `null`，核心会如实报告"事件没有 session 标识"，而不是假装知道哪个会话是活动的；
- 同时记录一条 `session-id-missing` 日志并带上**该对象的键名**，这样下一次真实运行就能直接看出正确字段，而不用再猜。

这是刻意的选择：宁可功能降级为"拒绝自动播放"，也不编造一个可能张冠李戴的会话身份。

## 测试证据（8 项）

1. 活动 Session 是最新者，且空闲后不再活动；
2. 正在播放时**任何** Session 都被拒绝（含活动 Session 自己）；
3. 注册表在大量会话下保持有界，且只报告 id 前缀；
4. 两个并发会话：B 的活动**不影响** A 正在播的曲目（播放实例与状态都不变）；暂停后任何事件都不能开始播放；
5. 不允许触发自主播放的事件（如 `tool/call`）仍会记录活动 Session；
6. 临时会话增量**小于**完整权重增量，且上限生效；
7. 上限经重启仍生效（不同会话互不影响，说明上限是**按会话**而非全局）；
8. 没有会话上下文的收听保持满权重，不会被静默削减。
