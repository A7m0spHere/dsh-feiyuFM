# U23：界面收敛与播放控制响应

2026-11-01，用户反馈 UI 杂乱，暂停／下一曲点击后反应不流畅，其余体验正常。按本次反馈先处理界面与控制链路；候选补给、推荐质量和真实 FFT 的接续仍在 [PROJECT_PLAN](../PROJECT_PLAN.md)。

## 实现与修订

- 主面板聚焦当前播放、反馈和歌单；歌单首屏 3 首，其余展开。模式、听歌偏好、今天停止、曲库／平台、反馈管理和界面选项统一收入“电台设置”，主面板默认收起，DSH 设置席位默认展开。待播池计数与本批说明收入原有推荐设置。保留 U12/U13 小开关和素材、U19/U20/U21 入口。
- 播放命令立刻显示各自的处理中状态。待确认的重复换曲不重发；暂停可以取代当前页面待确认的播放／换曲，取消旧 RPC 等待、忽略迟到应答／错误。每个写请求拥有自己的超时和取消控制器，旧请求不能误清新请求的等待状态。
- Core 原本就先确认命令并异步准备音频，本轮未改变该行为。`resolving/selecting` 或待确认期间，客户端每 500ms 串行读取轻量快照，隐藏或取消订阅即清理；稳定时沿用 2200ms 普通刷新。`fishfm/state` 新增可选 `playbackOnly:true`，仅返回权威 snapshot，不查曲库／画像／模型。不增加模型调用。
- 悬浮条直接提供播放／暂停、下一首，抽屉与菜单继续可用。主面板、浮条共享同一个控制器和 Core；没有把音频迁入页面。

行为只在 [MVP §5](../MVP.md) 定义，RPC 与快照顺序见 [控制契约](../CORE_CONTRACT.md)。来源为本次源码修改，没有引入社区项目代码、素材或新运行依赖。

## 验证方法与证据

Windows、Node 24.22.1。客户端生成 bundle 已同步。检查入口：

```powershell
node --test --test-timeout=30000 test/dsh-client.test.mjs test/dsh-settings.test.mjs test/ui-presentation.test.mjs
$env:FISHFM_TEST_REAL_AUDIO='0'
node --test --test-concurrency=2 --test-timeout=30000
npm run build
npm run audit:acceptance
```

新增回归覆盖：慢换曲时立即反馈、重复点击合并、暂停抢占、旧成功／失败不覆盖暂停、准备时继续读取轻量状态与恢复普通刷新，以及 Host 轻量读取不加载其他投影。真实媒体跳过与模拟验证不作为音频通过。

Chrome 独立 headless profile 打开生产客户端 bundle 的本地模拟预览，检查 1440×1000 浅／深色、760×960 和 520×960 视口、展开设置、对话中的悬浮条。520px 视口另扣除预览的 280px 侧栏，是极窄内容区域；修复头部操作溢出后，该视口主页面无横向滚动溢出，760px 视口展开设置也无横向溢出。

预览给 next 的应答人为增加 1600ms 延迟；观察到“切换中…”、暂停按钮仍可用，暂停确认后迟到的 next 成功应答不撤销暂停；真实 Core 的延迟、平台取链和音频输出未在该页面模拟。浏览器无未捕获异常。复现脚本、截图与原始输出保存在本机忽略目录 `work/u23-controls-20261101/`，可交付的脱敏结论见 [结果附件](assets/U23-controls-results.json)。预览的 `window.__fishfmPreview` 只在原有开发预览页提供，不进入生产 bundle。
