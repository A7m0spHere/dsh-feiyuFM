- 状态：**测量工具与加速跑已可用**；**两小时的真实运行尚未做**（需要 P3 的真实播放环境）。本文区分这两者。

## A09 的声明需要可测量，而不是断言

A09 要求"连续两小时自动听歌、用户未主动聊音乐、**新增 LLM 请求数为 0**"，证据是"请求计数、工具注册/上下文注入检查与脱敏运行日志"。因此本轮做的是**测量能力**：

| 测量项 | 实现 | 为什么这样测 |
|---|---|---|
| 音乐层请求计数 | `src/runtime/recorder.mjs` 按种类计数：`local` / `platform` / `computation` / **`model`** | "没有模型请求"是一个**计为 0 的数**，不是看法。计到 1 会额外记一条显式事件，不可能被忽略 |
| 提示面是否静态 | 记录一次工具/命令注册，长跑中**注册次数必须保持 1** | "不在每轮注入音乐状态"的可检验形式就是"只在加载时注册一次" |
| 资源基线 | 定期采样 RSS/heap（Windows 上还采集工作集与句柄数、fishfm 子进程数） | 慢泄漏看不见，所以要么采样要么不知道 |
| 趋势判定 | `summarizeTrend` 用**前后半段均值**比较，>10% 判为 growing | 端点比较太容易被噪声骗，且它会明确说"样本不足，不做判断" |
| 脱敏 | 报告只含计数、尺寸、标签与时间 | 会话材料、解析出的 handle、媒体 URL 都不进报告；有测试逐项断言这些字符串不出现 |

采样/探针在拿不到数据时返回 `null` 而不是编造数字——**编造的资源数字比没有更糟**。

## 加速跑（`npm run soak`）

```powershell
npm run soak                              # 默认 5 分钟加速跑（合成 provider 需 --fake）
node scripts/soak.mjs --minutes 0.75 --interval 3 --fake
node scripts/soak.mjs --minutes 120       # 真实两小时（需要已登录的真实适配器与真实音频）
```

一次 45 秒加速跑的真实输出：

```
[soak     3s] after opt-in: status playing, current soak-5
ran for 0.79 minutes (requested 0.75)
autonomous selections: 3 · session events: 9 · tracks played: 2
model requests from the music layer: 0
prompt surface registrations: 1
memory trend: stable — memory did not grow meaningfully between halves
```

也就是说加速跑**真的走完了闭环**：自动选歌 → 解析 → 播放 → 进度 → 结束 → 成长 → 再选下一首。

## 三个让长跑"看起来通过但实际没测到东西"的坑（都已处理）

1. **没有 provider 时整场跑不出声**：宿主没有装适配器时，选歌成功但解析报 `provider_unavailable`，于是"0 个模型请求"这句结论是在一个**什么都没播**的会话上得出的。现在 `--fake` 会带一个合成 provider，并且**开场就打印是否真的开始播放**；没播就明确说"以下数字描述的是一个空闲会话"。
2. **复用上一次的数据库会让这次白跑**：核心会记住"当前曲目"，重开旧库会把那首恢复成 `current`，于是选择逻辑**正确地**不再选新曲（而新的播放后端什么都没播）。现在默认用干净数据库，要续跑必须显式 `--resume`。
3. **加速跑必须真的听完几首**：曲目时长 3 分钟时，45 秒的跑法一首也听不完，"完成的有效收听数"会是 0。现在加速模式下用 12 秒短曲目，两小时模式仍用 3 分钟真实时长。

另外修正了"自动选歌次数"的计数口径：原先在事件回包上看 `selected`，而音乐通常是在**上一首结束**时接上的，所以恒为 0；现在按 `selectedBy === 'agent'` 的去重播放实例计数。
