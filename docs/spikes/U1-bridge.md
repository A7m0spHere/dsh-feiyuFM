## 桥接（`src/ui/bridge.mjs`）

ARCHITECTURE 定下的三条规则，逐条实现并可测：

| 规则（出处） | 实现 | 测试 |
|---|---|---|
| 重连先取快照，再消费较新的 revision，**避免旧状态回放** | 连接后主动 `snapshot`；`revision <= 当前` 的状态一律丢弃并计数 | ✅ |

## 一个只有对着真实宿主才暴露的问题

我先按"想象中"的协议写了桥接，然后拿**真实核心宿主的输出**喂进去——**接受 0 条**。实际形状是：

- 问候是 `{type:'ready', protocol, snapshot}`（不是 `hello`）；
- 状态推送是 `{type:'state', reason, snapshot}`，**revision 在 snapshot 里，不在信封上**。

第二条是真正要紧的：ARCHITECTURE 要求按 revision 丢弃旧状态，而**宿主的推送信封上根本没有 revision**。桥接现在从两处读取（信封或 snapshot 内），并有一条测试用**从真实宿主抓下来的确切形状**驱动它。修好后同一次集成检查：接受 3 条、0 条被拒、revision 正确推进。

教训与之前几次一致：**协议要对真家伙验证，不能对着自己的假设验证**。

## 窗口位置（`src/ui/window-state.mjs`）

MVP 第 5 节要求位置记忆，以及**多屏断开或 DPI 变化后窗口回到可见区域**。后者是容易出错的地方：记住的位置在一次显示器变化后可能完全在屏幕外，而一个够不着的窗口比一个默认角落的窗口更糟。

| 情形 | 行为 |
|---|---|
| 没有记住的位置 | 用默认位置（首选显示器右上角留边距） |
| 记住的位置仍可见 | 原样返回，**尊重用户选择**（贴边的窗口也算可见） |
| 位置不在任何显示器上 | 恢复到可见区域，并**说明原因**（显示器可能被拔掉），同时保留"用户当时选的位置"供查阅 |
| 尺寸超过显示器 / 缩放变化 | 夹到可放下的尺寸，并说明是缩放变化还是尺寸过大 |
| 没有任何显示器信息 | 原样返回，**不臆造布局** |

判定"可见"用的是**可用角落仍然在屏内**（阈值 48px），而不是"任意一个像素可见"。
