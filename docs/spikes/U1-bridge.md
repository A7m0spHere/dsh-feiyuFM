## 一个只有对着真实宿主才暴露的问题

我先按"想象中"的协议写了桥接，然后拿**真实核心宿主的输出**喂进去——**接受 0 条**。实际形状是：

- 问候是 `{type:'ready', protocol, snapshot}`（不是 `hello`）；
- 状态推送是 `{type:'state', reason, snapshot}`，**revision 在 snapshot 里，不在信封上**。

第二条是真正要紧的：ARCHITECTURE 要求按 revision 丢弃旧状态，而**宿主的推送信封上根本没有 revision**。桥接现在从两处读取（信封或 snapshot 内），并有一条测试用**从真实宿主抓下来的确切形状**驱动它。修好后同一次集成检查：接受 3 条、0 条被拒、revision 正确推进。

教训与之前几次一致：**协议要对真家伙验证，不能对着自己的假设验证**。

## 窗口位置（`src/ui/window-state.mjs`）

MVP 第 5 节要求位置记忆，以及**多屏断开或 DPI 变化后窗口回到可见区域**。后者是容易出错的地方：记住的位置在一次显示器变化后可能完全在屏幕外，而一个够不着的窗口比一个默认角落的窗口更糟。

| 情形 | 行为 |
|---|---|
| 没有记住的位置 | 用默认位置（首选显示器右上角留边距） |
| 记住的位置仍可见 | 原样返回，**尊重用户选择**（贴边的窗口也算可见） |
| 位置不在任何显示器上 | 恢复到可见区域，并**说明原因**（显示器可能被拔掉），同时保留"用户当时选的位置"供查阅 |
| 尺寸超过显示器 / 缩放变化 | 夹到可放下的尺寸，并说明是缩放变化还是尺寸过大 |
| 没有任何显示器信息 | 原样返回，**不臆造布局** |

判定"可见"用的是**可用角落仍然在屏内**（阈值 48px），而不是"任意一个像素可见"。

## 真实 IPC 传输（`src/ui/ipc.mjs`）

上一轮把桥接的传输留成"注入的"，并把 ARCHITECTURE 第 115 行的要求标为未做。本轮补上，并用**真回环 socket** 验证：

| 要求（ARCHITECTURE 115） | 实现 | 测试 |
|---|---|---|
| **只绑定回环** | 监听固定 `127.0.0.1`；**显式拒绝** `0.0.0.0`、`192.168.x`、甚至 `localhost`（它可能解析到非回环地址，按严格读法拒绝） | ✅ |
| **校验调用身份** | 共享令牌，写在`<状态目录>/ui-token`，**任何一行之前必须先过认证**；比较用 `timingSafeEqual`，长度不符时也先做一次等长比较再失败（不泄漏长度） | ✅ |
| **协议版本** | 认证通过后立即发 `ready`（带面板协议版本），面板在消费任何状态前先确认版本 | ✅ |
| **退出通知** | `close()` 先广播 `exiting` 并留出极短时间让消息发出，再断开；测试断言面板最后收到的是 `exiting`，且桥接据此**不再重连** | ✅ |
| 不可无限缓冲 | 单行超过上限即断开并记录；认证超时（5 秒）回收槽位 | ✅ |

**拒绝时不泄漏信息**：令牌不符时只回 `unauthorized`，不提示"接近了没有"；有测试断言拒绝消息里**不含**令牌前缀。

端到端：一条测试让**真 socket** 跑通"认证 → ready → 桥接请求快照 → 服务端回状态 → 桥接接受并推进 revision"，即整条 U1 链路在真实传输上成立。

## 仍未验证

- **真实窗口与真实多屏/DPI 事件**：属窗口壳（P0-05）。
- **令牌在 Windows 上的权限强度**：POSIX 上设了 `0600` 并断言组/其他无权限；Windows 的 mode 位只是建议性的，所以令牌文件放在**用户自己的状态目录**下，但这**不等于** ACL 一定私有（P0-06 已记录 .dsh 下文件的 ACL 情况）。
- **命名管道方案**：本轮选了本地回环端口。命名管道在 Windows 上能进一步减少暴露面（无端口、ACL 可控），但需要真实宿主实验确认可行性——ARCHITECTURE 说"IPC 选择基于实际宿主能力"，这一点仍待验证。
