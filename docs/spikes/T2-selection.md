## 顺序与门控（严格按 MVP 第 4 节）

1. **先过滤**：用户禁播（`ban_track` 约束）与"已知不可播放"（`isPlayable` 谓词，留给 P2/P4 提供真实能力）在**任何评分之前**剔除，且不计入候选数。
2. **再选池**：`discoveryRate` 决定是否尝试发现池。核心把 `discovery` 开关关闭时传 0，因此"探索开关"与"探索率"是两道独立闸门。
3. **后评分**：`affinity`（Agent 偏好，未见过则为 0.5）× 重复惩罚 + 新鲜度 + 小幅随机项；艺人偏好以 25% 权重微调。
4. **回退**：发现池没有可用曲目时退回熟悉池，**保留用户设置值**并记录 `fellBack: true` 与原因——对应路线里的"推荐不可用 → 退回熟悉池，记录本次没有发生探索"。
5. **等待**：没有候选时返回 `track: null`，调用方只尝试一次；核心不循环重试（测试用 `selectorCalls === 1` 断言）。

## 参数（首版，见 [DECISIONS 第 12 节](../DECISIONS.md)）

| 参数 | 值 | 理由 |
|---|---|---|
| 中性偏好 | 0.5 | 没见过的曲目不应因为"没数据"而吃亏 |
| 新鲜度加成 | +0.08 | 让没播过的不至于永远输给熟悉曲 |
| 重复惩罚 | ×0.45/次（6 小时窗口内） | 指数衰减，播得越多越难再被选中 |
| 冷却 | 30 分钟硬排除 | 刚播完的不进入候选，而不是"分数低一点" |
| 随机项 | ±0.05 | 只用于打破平局，不盖过偏好差异 |
| 历史窗口 | 最近 50 条 | 有界读取，避免历史越长越慢 |

## 可复现性（A05 要求"固定随机种子的选择结果"）

- 同一个种子在两条独立数据库上产生**完全相同的选择序列**（测试跑 20 次决策并逐项比对）。
- 宿主的选择器默认使用**存储里的 `agent_seed`**，因此重启后选择轨迹不变；换种子则轨迹不同（测试同时断言"相同"与"不同"）。
- 评分函数 `scoreCandidate` 是纯函数：同样的输入给同样的分数。

## 两种候选来源是互斥的，且已显式化

`selectionMode` 只有两个取值，避免"这条曲子到底从哪来"含糊：

- `environment`（默认，产品路径）：选择器每次决策都**实时读取**用户环境。测试验证"导入后立刻可选"，即它不是启动时缓存。
- `queue`：Phase 1 的固定候选调试入口（`setQueue`），供离线调试与旧测试使用。`--selection queue` 可切换。

## 本轮修掉的真实缺陷

1. **`recentPlays` 把时间戳钳到 0**：原先用 `Math.max(0, ended_at)` 初始化，任何**小于 0** 的时间戳都会被悄悄改写成 0，从而把冷却窗口算短。改为用行自身的值初始化（`-Infinity`）。**这是真实的逻辑错误**，只是生产时间戳通常为正才没暴露。
2. **空结果的原因含糊**：过滤前计数没保留，导致"还没导入任何音乐"和"候选全被过滤"都报 `no candidates`。这两件事需要用户做不同的事，现已区分为 `no candidates` / `every candidate was filtered out`，并暴露 `considered.offered`。
3. **`considered` 在成功路径缺失**：只有失败路径带该字段，现已统一，便于上层与 UI 展示"考虑了多少首、实际选了哪首"。

## 仍未验证

- **发现池目前恒为空**：推荐的平台接口属 P2/P4。因此探索率 100% 在现场只会表现为"回退 + 记录"，这是当前的**真实**行为，不是 bug；接上推荐接口后需要复测探索命中。
- **工作上下文权重**：MVP 提到按"工作上下文"评分，但 T2 未引入该维度——它依赖 I1 的活动 Session 判定，且路线要求不猜工作内容（现阶段不引入比乱猜更诚实）。
- **冷却与惩罚参数**：30 分钟 / ×0.45 / 6 小时均为首版取值，无真实听歌数据支撑。
- 用户"暂时不听"由 Core 的 `blockUntil` + 约束处理（Phase 1 已测），T2 未重复验证到期后的行为差异。
