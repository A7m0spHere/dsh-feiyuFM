# N20：项目检查发现的超时、筛选状态与预热问题

2026-10-06，用户要求检查项目 bug，并随后要求修复。此次修复不改变推荐范围、模型调用预算或暂停规则。

## 音频通信超时

`PipeTransport.request()` 在超时或同步写入异常时，先把当前请求从 `pending` 删除，再调用 `fail()` 关闭连接。`_closed()` 只拒绝仍在 `pending` 中的请求，因此被删除的请求永远无法结束。

修复前，用真实命名管道连接一个只接收、不应答的服务：30ms 超时，200ms 后连接已经关闭、等待表已经清空，但请求仍未结束。影响包括 Core 播放任务不能收尾、`waitForIdle()` 持续等待，以及宿主不应答 shutdown 时无法走后续强制退出。

修复为保留等待记录，统一由 `_closed()` 清理计时器并拒绝所有请求。新增真实管道回归覆盖超时请求及其他等待者同时收到 `command_timeout`，以及同步写入异常返回 `pipe_closed`；不依赖音频设备或生产进程。

## 模型筛选计数

`discovery.status()` 使用未加模型排名的原始 `usable()` 候选统计 `picked`，导致计数始终为 0。复现：候选实际已有 `llmRank: 1`，状态仍报告 `picked: 0、due: true、hasFilter: true`。

状态统计现在与选歌使用同一份 `stamped(usable())` 投影。新回归从 facade 到 Core 状态接口验证：已有可用排名且筛选比刷新新时，`due` 为 false；所有排名曲目不可用后，剩余未筛选曲目使 `due` 恢复 true。缓存外、不可播放的排名不计入 `picked`。相同事实的缓存、15 分钟冷却、每日次数和 token 预算仍由原有预留逻辑控制。

## 预热默认值复测与修订

N19 的“四个持有者即可快开”是当时测量结果，不是 WPF 的固定契约。本轮旧代码全量测试失败（预热后 4777ms），单独复跑也失败（4907ms），排除了仅由全量并发引起的解释。

使用真实 `PlaybackSupervisor` / `PlaybackService`、生成的静音 WAV 与 `pwsh` 重测：

| 已打开的持有者 | 冷 load | 填满后连续两次 load |
|---|---|---|
| 4 | 6018ms | 5128 / 5274ms |
| 8（诊断上界） | 5699ms | 644 / 514ms |
| 5（新的默认值） | 5428ms | 848 / 712ms |

临时诊断确认 5 个持有者均为 `opened=true、failed=false、HasAudio=true、NaturalDuration.HasTimeSpan=true`。4 个资源都打开仍不足以让当前机器稳定进入快路径；增加到 5 个可恢复快速加载。为何当前阈值与 N19 当时测量不同尚未定位，不能将本轮阈值推广到其他机器。

Node 后端、PowerShell 直接启动的默认值及非法环境值回落统一改为 5。显式 `FISHFM_PLAYBACK_WARM_HOLDERS=0..8` 继续覆盖默认值，0 关闭预热。持有者仍静音、从不播放、仅在真实播放期间逐个打开。首曲依然冷启动；`pwsh` 当前测量填池约需 20–30 秒，比旧默认值更久，时间随 shell 与负载变化。

性能测试按生产默认池大小等待就绪，保留原来的 **load < 2 秒且 < 冷 load 一半** 两条要求，没有放宽断言。独立回归结果：冷 9287ms，预热后 824ms，通过。全量测试中冷 11377ms、预热后 581ms，通过。

Windows PowerShell 5.1 后备路径使用同样的生成静音资源与 5 个持有者复验：冷 6419ms，后续两次 652/628ms。两种 shell 都经真实命名管道完成加载及退出，不仅做脚本语法检查。
