# N14：用户「下一首」在模型歌单无可播曲目时回退输入曲库

日期：2026-10-05。范围：`src/core.mjs`（next 命令）、`src/selection.mjs`（decide 透传选项）、`src/core-host.mjs`（buildSelector 回退池）、`src/insights.mjs`（解释文案）。无 UI 结构改动，不需要重建客户端 bundle。

## 用户报告与根因

用户在真实生产中报告：正在播放模型歌单曲目（Darkside，「你触发换曲 · 大肥鱼推荐」）时点「下一首」，弹「模型歌单暂时没有可用歌曲…(no_candidates)」。此前的 N12 修复（`cb39aaa`）只解决了"艺人核对失败导致核对通过数为 0"的问题，没有解决病根：

**LLM 模式下选择器只从模型歌单取候选（已知歌单歌曲→熟悉池、陌生歌单歌曲→陌生池）。当歌单核对通过的曲目全部是当前曲目、进入 30 分钟冷却、被禁播或标记不可用时，两个池同时为空，用户点「下一首」直接报错——尽管输入曲库里有数百首可用曲目。** 歌单每轮只有最多 6 首、核对通过更少，连续换曲几次必然耗尽，这是该警告反复出现的结构性原因。

## 修复设计

- **用户主动「下一首」是明确的换曲意图**：模型歌单没有可播曲目时，用同一套选歌规则（禁播/不可播过滤、30 分钟冷却、排除当前曲目、偏好/重复/反馈评分）回退到输入曲库选一首，决策记录 `fallbackReason='模型歌单暂时没有可播的曲目，已回退你的输入曲库'`；「大肥鱼说」回复如实说明回退来源。
- **自主续播（曲终/会话事件/自主启动）不回退**：仍只从模型歌单选择，歌单耗尽时保持等待，符合 N11"模型决定推荐哪些歌"的产品定义；恢复/自主启动的报错消息区分是否已尝试回退。
- 平台兼容模式行为不变（其熟悉池本就是输入曲库）。
- 两个来源都耗尽时才报 `no_candidates`，消息如实列出"模型歌单和输入曲库"。

## 实现

- `selection.mjs` `decide` 改为接收完整 options 并透传给 `listFamiliar`/`listDiscovery`（既有闭包忽略该参数，兼容）。
- `core-host.mjs` `buildSelector` 的池闭包在 LLM 模式且 `options.libraryFallback` 时改用输入曲库（environment + 已知 + 喜欢，与平台模式同源）。
- `core.mjs` `next`：歌单无候选时以 `libraryFallback:true` 重试一次；成功则覆盖 `fellBack`/`fallbackReason`；仍无候选才抛 `_noCandidatesReason(true)`。

## 验证

- `npm test`：357 项全过。新增 `a user next falls back to the library when playlist songs are exhausted, autonomy does not`（歌单歌曲冷却后用户下一首回退曲库另一首、自主续播保持等待、全部耗尽才报错且消息包含两个来源）；更新 N12 时代"空歌单下一首报错"断言为"回退输入曲库"；更新真实 Core 桥测试的下一首报错文案断言。
- `npm run check`（113 模块）与 `npm run build`（含调试冒烟）通过。

## 未验/边界

- 真实宿主中的回退选歌与「大肥鱼说」回退文案未现场验证（生产插件未重载）。
- 回退决策的 `pool` 仍记为 `familiar`（它确实来自熟悉池），回退本身以 `fallbackReason` 区分；选歌依据面板通过回复文本呈现。
- 歌单耗尽的自动出路（低频自动生成新歌单）不在本轮范围，仍按 N11 的自动更新门控走。
