# P0-08：合并审查后的客户端状态修复

2026-11-04。用户授权修复审查发现的两项 P2。先在 `fix/netease-initial-state` 修复公共客户端，再同步到 P1；不合并 main、不发布 npm，不操作日常数据、账号或凭据。

## 已复现的问题

1. 初始化的独立曲库读取或旧轮询晚于导入／清空应答返回时，库代次没有失效，旧结果仍可覆盖新显示。受控复现为导入 5 首后回到 0 首、清空后显示旧 9 首；实际数据库不因此回滚，但界面和首次播放入口会使用旧数据。
2. 平台操作只挑选 snapshot／library／persona，丢失 `platformError/libraryError/libraryPending`。通过真实 settings handler 和模拟 Bridge 复现退出已确认、平台读取失败后，界面仍显示旧 authorized、可导入且没有扫码入口。

这些是受控 RPC 时序与分项故障回归，不是修改真实账号或曲库。先构造九项反例，均先失败后通过；随后补充“旧轮询恢复授权／清掉新错误”两项反例，同样先失败后通过。新增合计 **11/11**，跨分支的最终计数以结果 JSON 和 PROJECT_PLAN 为准。

## 最小修复

- 导入、清空与撤销恢复确认后推进客户端曲库代次，取消确认前的独立读取；旧查询和旧轮询由既有代次检查拒绝。
- 写入时若用户另选了查询或页码，不应用旧写响应中的曲库页，而用当前选择重新读一次。写响应延迟曲库时同样复用既有 `fishfm/library`。
- 轮询和平台操作复用同一投影，保留分项错误；实际数据恢复才清错。平台读取失败时清空可用性缓存，显示失败／重试，不沿用旧 authorized。单独曲库失败保留缓存和平台入口。
- 独立平台代次只保护平台字段，旧轮询不能恢复退出前的授权或清掉更新后的错误，不中断播放快照和独立曲库读取。
- 同步生成客户端 bundle；没有新 RPC、服务、依赖、音乐库字段、推荐或播放改动。真实授权验证留在 Core。

## 覆盖

| 场景 | 期望 |
|---|---|
| 独立读挂起 → 导入／清空／撤销成功 → 旧读返回 | 新曲库不回滚，旧等待已取消 |
| 旧状态轮询 → 导入成功 → 旧轮询返回 | 库和播放快照均保持新结果 |
| 导入期间选择新搜索／页码 | 旧页不覆盖当前选择，重新读取当前页 |
| 导入或歌单读取的响应携带 libraryPending | 独立读取一次，不一直沿用缓存 |
| 退出已确认、平台状态读取失败 | 明确失败、无可用授权缓存或导入按钮，可重试 |
| 后续平台响应成功 | 清除旧 platformError，恢复真实账号操作 |
| 单独曲库读取失败／恢复 | 保留缓存及登录入口，正确显示／清除 libraryError |
