# N21：播放中断检测与有界恢复

日期：2026-10-07。用户报告偶发播放中断，要求检查项目并优化。本轮确认源码缺口并做故障注入验证，未取得当次生产中断日志，不能将所有中断归因为同一原因。

## 确认的问题与修复

1. WPF `MediaFailed` 只设置标记，只有媒体打开阶段读取它；已开始播放的音频失败后不会向 Core 发错，状态可能一直显示播放中。现在播放泵上报一次 `media_failed`，从事件参数读取真实异常；错误分类保留在宿主快照中，断线也不会丢失。
2. 播放状态为 `playing`、时间线不再推进时没有退出路径。现在从 play 或最后一次实际推进计时，连续 15 秒不动上报 `media_stalled`。短暂缓冲、真实进度推进和暂停不触发；使用单调时钟，不按 UI 插值或歌曲元数据推断曲终。
3. 断线时发生的 `ended/error` 没有在重连快照中补发；歌曲结束后 Core 仍保留旧曲目而不续播。现在匹配实例/版本后补发终态一次，不补计失联时段的有效收听。
4. 旧恢复任务在 await 后失败，可能清掉已换上的新曲目；snapshot 超时还可能递归触发并行恢复。现在每实例/版本共享恢复任务，最多三轮连接/快照尝试，每次等待后检查实例和版本。新曲目可以独立恢复，旧任务不能清掉新状态。
5. 宿主丢失、持续卡住或可重试媒体错误原先直接终止原曲。现在 Core 重新解析一次，沿用 `playInstanceId`、有效收听累计、静音设置和最后已确认位置；seek 不支持时如实回到 0。过期地址与中断恢复共用同一次预算。恢复递增命令版本，重复旧事件失效，暂停/换曲可取消恢复。
6. 恢复 load 失败时原 `_launch` 丢弃已听片段。现在已 started 的实例按实际累计记录一次 `error` 历史，未开始的加载仍不伪造收听。自主媒体失败保留原有最多两次候选替换预算，卡住候选暂排除 5 分钟；播放服务丢失不把歌曲标为不可播。

主面板/设置与悬浮抽屉显示中文恢复或失败说明。本轮不改变模型调用、推荐来源、账号与预热池规则。

## 验证

- 新增 15 项回归，覆盖三类中断的原曲恢复/仅一次预算、静音/位置/有效时间保持、暂停和换曲取消、恢复失败历史、失联终态、await 竞争、连接恢复预算、新旧恢复并存、断线曲终后真实命名管道续播，以及真实播放子进程退出后恢复。
- 旧 HEAD 对照：八项断言失败（三类原曲恢复、两种失联终态、两种旧恢复竞争、WPF 播放泵）；两项等待恢复的取消测试超时，随后改成有界等待检查。修复后均通过。
- WPF 播放泵测试通过 PowerShell AST 提取实际宿主函数，在 `pwsh` 和 Windows PowerShell 5.1 下执行受控时间线/错误注入；它证明函数语义，不冒充真实网络中断或解码器故障。
- `npm test`：**408/408，通过，零跳过**。包含现有真实 WPF 预热、媒体打开取消回归；子进程退出/断线续播使用协议一致的 fake backend，不触碰用户音频或账号。
- `npm run check`：**126 模块**；`npm run build`：构建及 debug smoke 通过；`npm run audit:acceptance`：10/10 证据项、69 份文档零坏链接；`git diff --check` 通过。审计只证明证据/引用存在，不提高生产验收状态。

## 部署边界

未重载生产 DSH、未操作用户数据库/平台账号，npm 仍为 `0.1.0-beta.1`。源码修复不代表已发布包或生产环境已包含修复；生产偶发中断与两小时运行仍待实际加载后观察。15 秒的连续停滞会触发一次重新获取，恢复速度仍受平台网络和 WPF 冷启动影响。
