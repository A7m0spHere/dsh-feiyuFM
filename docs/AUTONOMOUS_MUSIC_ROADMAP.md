# 自主听歌、偏好成长与新歌推荐实施规划

编写日期：2026-10-02。目标：把已经可播放的网易云插件推进到可解释、可持续体验的“导入音乐 → 自主选歌 → 有效收听 → 偏好成长 → 发现陌生歌曲”闭环。

本文维护实施设计、分阶段完成标准和后续扩展方向；任务状态、下一项和跨设备交接统一维护在 [PROJECT_PLAN](PROJECT_PLAN.md) 的 N0–N8 中。当前行为仍以 [MVP](MVP.md)、[CORE_CONTRACT](CORE_CONTRACT.md) 和可运行代码为准。文中的新增字段、接口和参数是实施建议，落地时同步契约与决策记录，不能把规划当作已有能力。

## 1. 要交付什么

近期交付以网易云为主，QQ 保留后续接入范围。已有 PHL 风格主面板、曲库和悬浮条继续使用；鲸鱼娘只表达播放器状态。后续 UI 重点是让用户看懂自动行为，不再先扩大装饰和动画范围。

完成后，用户可以：

1. 导入近期音乐、喜欢列表或指定歌单，看见真实来源、数量和更新结果。
2. 点击“你自己选”后离开面板，插件从可用候选中选歌，曲终正常续播；暂停、禁播和关闭自主听歌始终优先。
3. 看见这首歌是用户点播还是自主选择，是熟悉歌曲还是陌生候选，以及简短的选择依据。
4. 看见导入环境与 Agent 偏好分别是什么，哪些偏好由初始化产生，哪些由有效自主收听产生。
5. 在探索可用时听到曲库以外的真实歌曲；候选不足、权限不足或接口不可用时，看见实际原因。
6. 持续使用后核对偏好变化、重复率和发现结果，而不是只能凭“好像更懂我”判断功能是否运行。

这里的自主听歌是 Core 的音乐选择和播放经历。DeepSeek 可以通过明确工具命令控制它，但不会逐首调用模型评价，也不声称模型理解了音频。自动流程新增 LLM 请求保持为 0。

“根据喂的歌曲形成推荐风格”分两层交付：先让曲目、艺人和有来源的关系参与陌生歌曲选择；后续有足够可靠标签时再形成流派等风格画像。没有数据支持时，只展示艺人倾向和来源结构，不生成情绪、节奏或流派结论。

## 2. 起点与缺口

以下是 2026-10-02 对当前代码与证据的核对，不是长期不变的状态表。

| 能力 | 当前依据 | 下一步缺口 |
|---|---|---|
| 网易云登录、导入、真实播放 | [P3 实测](spikes/P3-real-loop.md)：近期导入 100/300 首，点播、暂停/恢复、下一首、离开面板续播、停用/启用已验 | 喜欢/歌单备用来源、权限和 URL 失效仍待现场验证 |
| 自主选歌与曲终续播 | [Core](../src/core.mjs) 已有 `selectAutonomously()`，`ended` 后继续选择 | 真实自主连续运行、DSH 会话触发和多会话优先级未完成验收 |
| 库内选择 | [selection](../src/selection.mjs)：歌曲/艺人偏好、小幅随机项、冷却、重复惩罚 | 无工作上下文评分；真实不可播放过滤和小曲库耗尽需要补齐 |
| 初始偏好 | [taste](../src/taste.mjs)：来源偏置、有界随机扰动、歌曲/艺人权重、种子持久化 | 当前不是流派画像，也未按真实播放频次构造丰富环境权重 |
| 偏好成长 | [growth](../src/growth.mjs) 与 [Host 装配](../src/core-host.mjs)：有效进度阈值、有界增长、静音权重、会话上限、维护衰减 | 真实收听对照、崩溃事务边界、恢复位置与有效收听时间需要验证 |
| 新歌探索 | 选择器、探索率、协调器和缓存装配已有 | NetEase Provider 没有 `getDiscoveryTracks()`；推荐能力为不可用，发现池没有真实入口 |
| 风格与相似推荐 | 当前只按歌曲、艺人权重选歌；`normalizeTrack()` 仅保留基础字段 | 特征来源、艺人 ID、种子关系、标签与陌生候选排序尚未实现 |
| 两小时测量 | [recorder](../src/runtime/recorder.mjs) 和 [soak](../scripts/soak.mjs) 可做合成演练 | `soak` 使用合成曲目，人工注入进度/结束、会话事件和控制命令；计数并非全部来自生产调用，不能作为真实 DSH 两小时证据 |

历史 spike 文档按当时日期理解。例如 T3 曾记载“衰减未接调度”，当前 Host 已调用定时维护；后续以当前代码和新实测为准，不重复实现已有能力。

## 3. 阶段与依赖

| 阶段 | 任务 | 用户能得到的结果 | 进入下一阶段的条件 |
|---|---|---|---|
| 0 建立可信观察 | N0 | 能区分真实播放、合成演练、自动选择、手动操作和成长 | 采集来自实际运行链路，报告能定位一次播放 |
| 1 稳定自主听歌 | N1 | 在现有曲库中持续自主选歌，暂停与恢复不失控 | 真实完成多首自主续播，控制与历史一致 |
| 2 接入真实发现 | N2 → N3 | 能取得并播放曲库以外的歌曲，明确回退原因 | 推荐接口有证据，缓存和筛选可用，真实探索闭环通过 |
| 3 由输入塑造选择 | N4 → N5 | 导入音乐影响候选来源和排序，Agent 经历进一步塑造差异 | 特征有来源，输入/经历对推荐的影响可复现 |
| 4 把行为展示清楚 | N6 | 用户知道为什么播、实际探索了多少、偏好为何变化 | UI 与同一 Core 的诊断数据一致 |
| 5 长期体验与交付 | N7 | 连续两小时运行有可信证据，参数有体验依据 | 对应验收有结果，失败和限制如实记录 |
| 后续双平台 | N8 | QQ 复用已经验证的控制、发现与画像链路 | 用户恢复 QQ 优先级，真实接口先通过验证 |

推荐执行顺序：N0 → N1 → N2 → N3 → N4 → N5 → N6 → N7。N2 的只读接口验证不依赖 N1 完全结束，可以在自主播放现场实验等待期间推进；共享 Core、存储和契约变更仍串行落地。N6 的基础回退提示应随 N3 一起交付，不等到最后才告诉用户探索不可用。

QQ 不再作为网易云 T1/T2/T3、画像或 UI 的前置条件。两小时基线可以在 N1 后先跑一次，推荐与成长闭环接通后，再补覆盖新行为的最终长跑。

## 4. N0：先把真实行为测清楚

### 实施内容

- 保留 `scripts/soak.mjs` 的合成演练用途，明确标注 synthetic；新增或改造真实观察入口，附着在插件拥有的 Core/Playback 上，不对同一生产库另启第二个播放 Core。
- 真实运行不得注入模拟 `progress`、`ended` 或虚构 Session。自主开始由用户一次明确选择发起，其后由真实曲终和允许的 DSH 事件驱动。
- 音乐侧网络计数在实际 Provider/transport 入口采集；工具注册和上下文变化在实际 Adapter 注册/宿主入口采集。拿不到的指标标为 unknown，不能默认 0。
- DSH 正常模型请求和音乐引起的请求分别统计；两者对照的采集入口先验证。手工写入一次“注册”不能证明后续没有额外上下文注入。
- 每次运行记录代码提交、DSH/Node 版本、模式、设置、候选数量、起止时间和采集覆盖范围。资源采样覆盖 Core、Playback 和宿主可观测部分。

### 诊断数据建议

每次决策用 `decisionId` 连接 `playInstanceId`、选择者、池、候选数、过滤原因、回退原因、种子及算法版本；每次成长记录有效进度、结束原因、更新前后权重和拒绝更新原因。元数据可以脱敏入证据，Cookie、账号明细、音频 URL、聊天正文不进入报告。

先扩展已有 `lastSelection`、历史和 recorder；只有实际查询需要时再增加持久表。不保存每 400ms 的完整快照，采用状态变化事件和低频资源采样，设置数量/时间上限。

### 完成标准

一段真实短跑可以串起“自动决策 → 平台解析 → 后端开始 → 实际进度 → 曲终 → 历史 → 成长 → 下一次决策”。报告明确标识哪些事实来自宿主、哪些来自播放器、哪些不可观测。单纯运行时长足够、计数全为 0 或接口返回成功，都不算通过。

## 5. N1：稳定库内自主听歌和成长记账

### N1a：明确开始、续播和暂时不听

- 实测“开始听歌/你自己选”、Normal/Focus/Silent/Off、两个开关的四种组合，核对实际声音和进度来源。
- 默认开启自主权限不等于重启即播放。重启仍强制暂停；到期约束只解除限制，不自动解除暂停。
- 真实 DSH `turn/end` 只能在已有权限且没有当前曲目时尝试开始；没有可靠 Session 标识时采用已定义的通用上下文，记录原因，不猜活动会话。
- Focus 先验证减少主动动作、曲终可续播的已有语义。没有可靠工作分类和曲目特征之前，不承诺“写代码自动换纯音乐”。
- 暂停期间的旧解析、缓存刷新完成或晚到曲终，都不能恢复音乐；手动点播和手动下一首继续保留 user 来源。

### N1b：处理真实播放失败与候选耗尽

- 验证 URL 过期重解析、账号过期、权限不足、网络断开、播放器退出和重连。区分账号级、网络级与曲目级错误。
- 当前选择器的 `isPlayable` 默认允许候选，不能把它当作已接上生产权限过滤。补充本机可用性记录及有效期；确认不可播的候选应在后续决策时退出。
- 曲目级失败不写负面偏好。若允许自动尝试另一首，必须有决策预算和退避，超过预算等待并显示原因；网络故障不永久封禁曲目。
- 小曲库可能全部落入 30 分钟冷却。先明确显示等待原因；若放宽，只放宽重复冷却，不放宽禁播/暂停/权限，并记录规则与次数。
- 区分人格初始化种子与选歌随机流。当前 Host 重启会以相同种子重新建立 PRNG；核对这是否造成重复开场序列。若要接续随机轨迹，持久化随机状态或决策序号，并在决策提交时原子推进，不重新随机初始化人格。

### N1c：把位置和有效听歌时间分开

当前 Core 将 `positionMs` 写为 `effectiveMs`。需要重点验证重启后从旧位置恢复、资源重解析、seek 和后端位置跳变，避免把恢复到的时间线位置算作本次实际听过的时长。

建议增加独立有效进度累计：只累计同一有效播放段内、被后端确认的推进；暂停、睡眠、离线缺口、跳转和恢复起始位置不补算。保留 audio/logical、可听/静音的来源；未知时长不能伪造结束。迁移前定义旧历史的兼容语义，不能把缺失时长填成新的收听事实。

### N1d：核对成长门控、去重与崩溃恢复

- 当前成长门控主要检查 `selectedBy`、进度和结束原因。补测自主开关在播放中关闭、静音切换、恢复和跨 Session 时的语义，按 MVP 确保关闭自主听歌后不增加 Agent 经历。
- 当前历史插入与成长更新跨越 Core 钩子，不能仅凭单条历史唯一键声称整个成长事务可靠。选择“同一事务”或“持久待处理事件 + 幂等应用”方案，记录取舍。
- 用 `playInstanceId` 防止成长重复应用；崩溃发生在历史写入之后、成长之前时可以安全恢复，不能重复或漏算。重放本来不该更新的用户播放仍不更新。
- 保留有界步长、静音权重、Session 上限与衰减；真实运行记录更新与衰减的先后，不用当前权重的净变化替代全部经历。

### 完成标准

真实库内连续完成至少 5 次自主曲终交接，逐条有后端进度、历史和成长对照。短跑覆盖一次暂停保持、一次关闭自主、一次重启恢复；重启不自动出声。故障轨迹覆盖上述事务断点和晚到事件。5 次是最小现场闭环要求，不代表两小时或长期推荐质量已通过。

## 6. N2：验证网易云能提供哪些真实候选

先使用固定社区包 `@neteasecloudmusicapienhanced/api@4.40.1` 核对实际可调用方法，再选生产路径。接口名称、请求参数、账号要求、来源含义和许可在验证后记录，规划不指定未经确认的端点。

| 候选来源方向 | 用途 | 需要确认的问题 |
|---|---|---|
| 账号个性化推荐 | 尽快取得真实陌生候选 | 是否依赖登录；是否偏向账号原有口味；刷新周期与重复率 |
| 单曲相似关系 | 将导入曲目作为显式种子 | 是否可用；返回何种关系；覆盖范围；能否拿到时长和可播放资源 |
| 艺人关联歌曲 | 以可靠艺人信息扩展 | 是否有稳定艺人 ID；同名、多艺人、联合署名怎样规范化 |
| 歌单/标签关联 | 可选的风格扩展 | 标签来自平台、歌单还是推断；是否能归因到曲目；不得把歌单标签无条件当逐曲事实 |

账号推荐可以先提供“发现可用”，但它仍是网易云账号推荐，不等于 Agent 根据自己偏好推荐。两种来源分别记录与展示。

每个方向按“只读调用 → 规范化候选 → 去重/陌生筛选 → 资源解析 → 真实播放”验证。返回数据成功却没有任何可播放陌生歌，只能算该接口部分可用。

### 完成标准

至少一个来源返回真实候选，且至少一首不在用户导入环境、也没有插件有效收听历史的候选可以真实播放。记录平台版本、来源、限制、实际数量和失败类型。若全部来源不可用，保留库内自主播放，明确列出探索阻塞，不用搜索随机歌曲伪装个性化推荐。

## 7. N3：把候选接成可持续的发现池

### 候选契约

沿用 Registry 的 `getDiscoveryTracks(provider, options)` 边界，在已验证的 Provider 中实现；扩展共享能力检查，覆盖 available/degraded/unavailable、空结果、失败和取消。可保留规范化 Track 数组兼容路径，把来源和诊断信息独立封装；实施时同步 `CORE_CONTRACT`，不能无版本地改返回结构。

每个候选至少保留平台/曲目 ID、基础元数据、推荐来源、种子关系、取得时间和到期时间。曲目详情与来源关系分开保存，不把发现歌曲写成用户近期播放，也不自动加入用户种子环境。

### 陌生、熟悉与探索成功

- 第一版陌生候选定义：不在用户导入环境，且插件没有该曲目的有效收听历史；只能称“对本插件而言陌生”，不能证明用户从未听过。
- 发现候选通过有效自主收听后，可以进入 Agent 已知歌曲池，保留 discovery 来源；不得继续把它的每次重播算作新歌发现。
- 熟悉池可由用户环境与 Agent 已知歌曲组成，二者身份独立。历史已选但失败、秒切的曲目是否仍可探索，按 N1 的有效经历判定。
- 分别记录探索尝试、选中陌生候选、实际开始播放、完成有效收听。设置的 20% 是尝试概率，不是四个指标都应达到 20%。

### 缓存与调度

- selector 只读本地缓存，不在评分中发网络请求。登录恢复、导入完成、用户明确刷新、候选不足或 TTL 到期触发后台刷新。
- 单个 Provider 同一时间最多一个刷新；设置请求预算、超时、取消、退避与缓存上限。是否持久化缓存在实现时按重启需求决定，不存音频句柄。
- 缓存区分成功但为空、能力缺失、账号过期、临时请求失败、正在刷新。临时失败保留仍有效的缓存，账号退出/切换时清理账号相关候选和请求。
- 探索关闭时停止主动发现请求；迟到刷新不能绕过开关触发播放。启用探索只允许补候选，不自动解除用户暂停。
- 分离页面展示上限与 selector 的实际曲库范围；现有 Host 库投影最多 300 首、熟悉池读取最多 5000 条，后续导入扩展要验证截断不会悄悄改变选择范围。

### 初始调度参数建议

| 参数 | 建议起点 | 调整依据 |
|---|---|---|
| 单批候选 | 40 首 | 沿用现有刷新默认值，实测陌生/可播比例后调整 |
| 缓存容量 | 200 首/平台 | 控制启动与筛选成本，按候选重复率评估 |
| 缓存 TTL | 6 小时；平台限制更严格时服从平台 | 实测刷新周期和账号推荐变化 |
| 低水位 | 可用陌生候选少于 10 首 | 避免每首都触发请求 |
| 最小刷新间隔 | 30 分钟；明确手动刷新另设有界限制 | 减少重复网络工作 |
| 曲目级失败替换预算 | 单次最多 3 个候选 | 防止连续换曲和请求循环 |

这些是拟定参数，尚未实现、未获真实质量验证；N3 完成时在 DECISIONS 记录最终数值与证据。

### 完成标准

离线覆盖探索率 0/20/100%、陌生筛选、候选重复、全不可播、缓存过期、旧请求取消和池耗尽。0% 不自主选发现池；100% 在发现池可用时选陌生候选；空池回退且理由可见。20% 用固定种子多次决策验证概率行为，短时真实体验不要求比例恰好为 20%。真实 DSH 完成一次陌生曲目的自主选择、播放、有效收听与来源保留。

## 8. N4：让“喂入音乐”形成有证据的环境画像

### N4a：先做好输入及更新

- 验证近期 → 喜欢 → 歌单的备用来源，允许用户明确选择输入歌单；音乐从何而来、实际导入多少、多少是重复始终可查。
- 不覆盖已有 Agent 偏好。新增歌曲补充初始偏好，已有歌曲只更新可靠元数据；按明确策略维护环境事实，不悄悄重塑人格。
- 当前 `user_environment` 对重复曲目保留首次来源；若同一曲目兼具近期、喜欢或多个歌单身份，新增来源关系/事实记录，避免第一批导入永久遮蔽后续输入。
- 真实次数/日期存在时才使用，未知保持未知。频次先做有界变换，防止一首高频歌曲压倒全部输入；回退来源和手动指定歌单不伪造频次。

### N4b：特征从确定的层级开始

| 层级 | 可以用于选择的特征 | 不足时的处理 |
|---|---|---|
| 必需 | 曲目 ID、艺人 ID/成员、来源、时长 | 缺少艺人 ID 时标记降级，不凭同名合并艺人 |
| 优先 | 经验证的相似关系、艺人关联、用户明确歌单种子 | 关系缺失时依靠曲目/艺人和探索随机性 |
| 可选 | 平台明确给出的语言、流派和标签 | 保存来源、置信度、更新时间；未知不填默认流派 |
| 后续 | 节奏、能量、情绪或音频特征 | 当前不承诺；需要独立数据/成本/许可验证，不从标题臆测 |

注意 `normalizeTrack()` 当前会丢掉新增特征。实施时同时更新 normalization、storage、Provider 转换、Host 投影和必要的 UI 展示，避免 Provider 拿到了但选择器用不到。

### N4c：环境和偏好分开

用户环境画像回答“用户提供了哪些音乐”；Agent 偏好回答“独立初始化后，哪些有效自主经历改变了权重”。两者分别存储、分别展示，外部收藏与评价不能直接赋值给 Agent 偏好。

初始画像仍保留固定种子和有界扰动。新的艺人/特征偏好初始化要明确重算与补齐规则：补缺失项，不覆盖听出来的已有项。特征版本、画像版本和数据覆盖率一并记录，算法升级不在后台静默重置全部偏好。

### 完成标准

准备至少两组来源可确认、分布明显不同的受控种子库，相同算法/随机种子下得到可解释的不同环境画像；重复导入和重启不重写已有偏好。有流派/标签数据时展示覆盖率，缺失时明确只能形成歌曲与艺人层面的画像。

## 9. N5：用种子和 Agent 偏好推荐陌生歌曲

### 两级推荐

1. 候选生成：从导入环境与 Agent 已知歌曲选取多个种子，通过 N2 已验证的关系获取候选；保留账号推荐作为另一种来源。
2. 本地排序：在可用陌生候选中，结合 Agent 偏好、用户环境的弱权重、种子关系、新鲜度、多样性和随机项排序。

未知歌曲没有直接 affinity 时，从可靠艺人/特征/关系估计，再回退中性值；未知不是不喜欢。最终过滤仍先于评分，暂停/禁播不能被高分候选绕过。

建议把当前评分扩展为可分解的项，不先引入复杂模型：

```text
候选得分 = Agent 倾向 + 用户环境弱影响 + 可证实的种子关系
         + 新鲜度 + 有界随机项 - 重复惩罚 - 过度集中惩罚
```

每项归一化并记录版本。随机项不盖过明确差异；环境权重弱于 Agent 倾向。具体权重用 N4 的受控数据及真实样本调整，不把规划中的公式当生产参数。

### 随机推荐的具体做法

当前“最高分 + 小随机项”可能长期只在少数高分歌曲中变化。先保留它作为基线，再比较“前 K 个候选按有界权重抽样”等简单方案：候选质量仍由评分控制，随机抽样增加覆盖，不能直接全库盲抽替代偏好。没有明显收益时保留基线，避免为了随机而扩大算法。

评价时同时看受控重放、唯一曲目率、艺人集中度和高相关候选的覆盖。相同随机状态可重放；不同抽样不能突破禁播/冷却等过滤。若未来需要用户选择纯随机模式，单独定义其范围和控制语义，不把现有探索率当成随机强度。

### 避免只围着同一位艺人转

- 种子分层采样，不只取 affinity 最高的一首；对高频艺人设置候选/连续播放预算，保留不同艺人和关系较远的候选。
- 探索率控制熟悉与陌生池选择；发现池内部的相近/宽松候选比例属于另一层策略，不能混作同一个百分比。
- 冷却、重复惩罚和成长衰减仍保留；不靠放大初始随机扰动证明形成了独立人格。
- 明确用户反馈属于用户环境或约束。若以后增加“我喜欢/不喜欢”按钮，先定义其语义，不直接让用户反馈覆盖 Agent affinity。

### 完成标准

固定候选池和随机种子，分别改变输入环境与 Agent 经历，核对候选排序的变化来自哪个因素。相同输入、版本与随机状态应可复现；重复导入不重置偏好；同一种子长期循环不能让一个艺人无限占据候选。真实账号至少取得并播放一首带明确种子关系的陌生歌曲，能追溯种子与来源。

如果只有账号推荐可用，N3 可以通过，N5 保留未完成；不能把平台账号口味称作 Agent 独立风格。如果只有艺人关系可靠，则交付艺人层面的推荐并如实限制描述，流派画像继续等待数据。

## 10. N6：把推荐和成长展示清楚

延续 `src/ui/client/` 的既有结构，不重做一套视觉系统。新增内容按使用频率放置：

| 位置 | 内容 | 交互要求 |
|---|---|---|
| 主播放器 | 用户点播/自主选择、熟悉/陌生、推荐来源 | 点击可看简短依据；错误和回退有明确原因 |
| 探索设置 | 探索开关、目标概率、候选池状态、最近刷新/失败 | 保留现有保存语义；能力不可用时仍能看见目标设置和实际状态 |
| 主面板详情 | 最近自主选择、探索尝试/播放/有效收听、重复情况 | 明确分母、时间窗口和数据不足；不显示虚假成功率 |
| 偏好详情 | 歌曲/艺人倾向、初始化来源、有效经历与最近变化 | 区分用户环境与 Agent 偏好；标签不足时不展示虚构风格 |
| 悬浮条 | 当前歌曲、状态与已有控制 | 保持简洁，详细报告留在主面板；隐藏不影响音乐 |

选择理由由确定的评分项与来源映射生成，例如“来自你导入歌曲的相似候选”“偏好艺人相关歌曲”“探索不可用，改从曲库选择”。不逐首调用 LLM 写评价，也不写“听懂了你的心情”。

当前只有部分 lastSelection 诊断，前述丰富理由需要 N0/N3/N5 提供数据。UI 不另算偏好或有效进度，认证 RPC 只暴露必要投影。键盘、暗色、窄窗口、系统减少动态效果继续覆盖；不在每轮主聊天插入音乐说明。

## 11. N7：真实验收和长期体验

### 三种证据分别记录

| 证据层 | 要证明什么 | 推荐方法 |
|---|---|---|
| 离线受控轨迹 | 逻辑、取消、概率、存储、去重、排序变化正确 | 固定时钟/种子、可控响应、故障点和迁移测试 |
| 真实短跑 | DSH/Provider/Playback 实际接通 | 真账号、真曲终、真实进度与用户声音核对 |
| 真实持续体验 | 自动续播稳定、发现有内容、成长不失真 | 两小时基线；其后按累计有效经历观察参数 |

### 两小时验收步骤

1. 记录运行版本、数据库基线、导入库、开关/模式、发现能力、候选池、资源基线和计数覆盖范围。
2. 用户明确开启自主听歌；此后正常使用 DSH，基线段不再手动点歌或定时暂停/恢复。只接受真实后端事件和宿主事件。
3. 运行至少 120 分钟，持续采集有效进度、曲终、选曲、成长、平台请求、音乐新增模型请求与资源趋势。
4. 暂停保持、断网、睡眠、模式切换和重启另设干预段，报告区分基线与干预；干预不能伪装自然自主行为。
5. 结束后对照 SQLite、后端事件和 UI，核对每个播放实例的经历与去重。不能用最终播放位置直接替代有效听歌累计。

### 必须给出的结论

- 真实持续时间、自动完成曲数、交接次数及失败/停顿原因；全程没有播放或依靠模拟事件推进则不通过。
- 音乐自动流程新增 LLM 请求数为 0，DSH 对照与采集覆盖完整；未知指标保留未验。
- 暂停、禁播、关闭自主开关不被撤销；停用清理成功；重启恢复暂停。
- 探索率设置值、探索尝试数、陌生选择数、实际播放数、有效收听数分别列出；关闭探索不会继续主动请求新候选。
- 历史和成长没有重复累计、墙钟补算或恢复位置误算；用户点播不成为 Agent 成长。
- Core/Playback/宿主资源没有未经解释的持续增长。现有趋势判定是筛查线索，疑似泄漏需延长观察和定位，不能仅凭一个百分比下结论。

两小时主要验证运行稳定性，不足以证明推荐质量或音乐人格成熟。QQ 暂缓期间，网易云专项里程碑可以通过，完整双平台 A01 与 v0.1 仍按原要求保留状态。

### 后续体验记录

建议按累计有效自主收听分段观察：首次 20 次检查成长是否实际发生；累计 100 次观察歌曲/艺人集中和陌生有效收听；有至少 3 个不同日期的体验后再讨论长期变化。这是采样建议，不是质量保证或发布硬门槛。

记录近期/全期两种窗口的唯一曲目率、艺人集中度、探索各阶段转化、重复率、播放成功率和用户主动跳过情况。用户跳过只说明此次操作，不自动代表 Agent 讨厌。每次参数调整只改变明确的一组因素，保留版本与前后样本，不用缺乏对照的小样本宣布算法变好。

## 14. 后续扩展边界

- QQ：用户恢复优先级后，先验证真实接口，再复用推荐候选和特征契约；同名歌曲不跨平台强行合并，账号缓存与解析各自隔离。
- 显式风格输入：可以在可靠特征成立后增加用户选择“多一些某类音乐”的约束/环境输入，保留 Agent 偏好独立；自然语言模糊时展示可选项，不偷偷猜并长期保存。
- 工作情境：只使用可靠的结构化宿主信号或用户显式选择。上下文无法识别时保持通用策略；不读取主模型内部思考，不请求模型猜工作内容。
- 音频/歌词理解、Embedding、复杂推荐模型、主动人格反思和跨设备音乐数据同步继续排除在当前 v0.1 范围外。将来要推进时单独明确收益、数据来源和验证方法，不自动扩大此次实现任务。
